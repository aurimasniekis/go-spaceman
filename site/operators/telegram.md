# Telegram setup

This page is for the person who runs central. It sets up the Telegram bot and Mini App described in the
[Telegram guide](/guide/telegram) (ADR-0083). Nothing here has been verified against a real bot yet
([Project status](/guide/status)); every example uses placeholder names.

## What you need

- A **bot** created with Telegram's BotFather (its token is a secret; SpaceMan keeps it sealed and write-only).
- For the Mini App, a **second DNS name** for central, such as `tg.central.example.com`, with its own TLS certificate.
  It must **not** be the host of `public_url`.
- A reverse proxy that **preserves the `Host` header** (SpaceMan routes on `Host` only and never trusts
  `X-Forwarded-Host`).
- Outbound access from central to the Bot API (`api.telegram.org`), and, in webhook mode, an HTTPS route from Telegram
  to central's main host.

## The Mini App host

The Mini App is served on its own host so that it never shares cookies with the web app. Set it in **two** places, and
make them the same name:

1. **Central's configuration**, `telegram.miniapp_host` (environment `SPACEMAN_TELEGRAM_MINIAPP_HOST`; see the
   [configuration reference](/reference/configuration#telegram)). It is a lower-case DNS name with no scheme, port or
   path, not an IP address.
2. **The bot's `miniapp_host`** (`spaceman telegram bot set --miniapp-host`, or the Terraform attribute).

They **must match the bot's host.** The configuration key is the one that matters for safety. Every request for that
host is served by the Mini App only, **whatever the bot's state**: with no bot, a disabled bot, a bot that failed to
start or an empty bot host, it answers `404` to everything and never falls through to the web app or the API. If the
two names differ, the configuration wins, the bot's is ignored (it still answers `404` and is never another name for the
main host), and the difference is logged, listed in the bot's `warnings` and shown on the System page. A bot host can't be stored while the configuration key is unset (the write is refused); the System page flags a stored host that has no key.

::: warning The provider needs central's key
The planned Terraform resource `spaceman_telegram_bot` sets the bot's `miniapp_host`, but **central's own
`telegram.miniapp_host` is not a provider attribute**: it lives in central's configuration file or environment
(deployment, not API state, for the same reason as `api_base_url`). Central refuses to store a bot `miniapp_host` while `telegram.miniapp_host` is not set in its configuration, so the
configuration key goes first, then the resource. Provider resources are planned (TG-12, in the provider's own
repository): until they ship, use the API or CLI.
:::

Changing the bot's host is a step-up, audited change.

## Webhook or polling

`mode` is `webhook` (the default) or `polling`.

- **Webhook.** Telegram posts updates to `POST /telegram/webhook/<hook id>` on central's **main** host. The path and a
  secret header are generated by central. Needs an HTTPS `public_url`. Central answers `200` at once and handles the
  update afterwards (an update still queued when central stops is lost; the bot's acknowledgements let people resend), or
  `503` when its queue is full so Telegram retries. Telegram reaches webhooks over IPv4 only.
  - Optionally set `webhook_ip_allowlist` (CIDRs, such as `149.154.160.0/20`; empty is off, which is the default). It is
    only safe when central sees the real client address: see the trusted proxy below.
- **Polling.** Central calls `getUpdates` itself. No inbound route or public HTTPS is needed. Use it for a development
  machine or when central can't be reached from the internet.

Configuring or changing the bot's token checks it with Telegram first (`getMe`), seals it and rotates the webhook
secret. Configuring a **different bot** (a different bot ID) **revokes every link**; deleting the bot, or giving the same
bot a new token, doesn't. The bot's health (`webhook_status`, who it is, whether the host is the configured one) is on
the System page and in `spaceman telegram bot get`.

## The trusted proxy

If a reverse proxy sits in front of central, list it in `http.trusted_proxies` so central reads the real client address
from `X-Forwarded-For` for every peer you listed and for no one else. Telegram's source-IP allowlist, the rate limits on
Mini App sessions and the refused-attempt audit rows all use that address; a proxy that isn't listed makes every
request look like the proxy. A proxy that drops idle connections (about 100 seconds) also needs the live streams'
heartbeat: `http.stream_heartbeat` (default 15 seconds, 1 to 45) keeps the Mini App's change feed and terminal stream from
looking idle.

## Setting it up

```sh
# central's configuration: the Mini App host (and trusted_proxies / public_url if you use them)
#   telegram:
#     miniapp_host: tg.central.example.com
spaceman telegram bot set --bot-token-file ./token --enabled --mode webhook \
  --miniapp-host tg.central.example.com
spaceman telegram bot get
spaceman telegram set-space --space payments --enabled --content-level summary
```

The token comes from a file or standard input and is never shown again. Setting the bot needs `system:write` and a
step-up. Planned Terraform resources (TG-12, provider repository): `spaceman_telegram_bot`, `spaceman_telegram_settings` and
`spaceman_space_telegram`, with a write-only `bot_token_wo`.

## Administration settings

Everything is configurable through the API and the [CLI](/reference/cli/telegram) (Terraform resources are planned), each change audited and
checked with `If-Match`. The one exception is the **Bot API base URL** (`telegram.api_base_url`, central's configuration
only): whoever sets it receives the token.

### Webhook behind a LAN-only `public_url`

Webhook mode registers the webhook under central's `public_url`, which Telegram must be able to reach over https. When
`public_url` is a LAN address, set `telegram.webhook_base_url` (environment `SPACEMAN_TELEGRAM_WEBHOOK_BASE_URL`) in
central's configuration to the public https address that routes to central, for example
`https://hooks.example.com`. The webhook is then registered under it; the webhook path and the secret-token check are
unchanged, and everything else (links, the Mini App) keeps using `public_url`. It must be https with a lower-case host
and no credentials, query or fragment. Like `api_base_url` and `miniapp_host`, it lives in central's configuration, not
in the API, the CLI or the Terraform provider, so the provider needs no change. Restart central: it registers the webhook again
at the new address when the bot starts.

Three things to know:

- A path prefix (`https://example.com/tg`) is for your reverse proxy: the proxy must strip the prefix before forwarding,
  because central serves only `/telegram/webhook/<id>`.
- The host must differ from `telegram.miniapp_host`: central would route the webhook to the Mini App, which answers
  404, so no update would arrive. Configuration validation and the bot API both reject the collision.
- The scheme must be lower-case `https://`; whitespace and `.` or `..` path segments are rejected.

> **Warning: the Mini App still uses `public_url`.** `telegram.webhook_base_url` only moves the webhook. The Mini App
> derives its origin from `public_url`, so a LAN-only `public_url` still breaks the Mini App until that is fixed in code.

### Bot

`enabled` (default off), `mode`, `miniapp_host`, `webhook_ip_allowlist`, and the write-only token. Delete turns Telegram
off; links stay and resume if the same bot is configured again.

### Policy and defaults

| Setting | Default | Range |
|---|---|---|
| `link_default_max_role` | `operator` | `viewer` or `operator` |
| `link_allow_admin_cap` | off | allow a link to carry the user's full grants |
| `link_sso_grants` | off | a link confirmed from SSO also carries SSO-mapped grants, until that session ends |
| `link_reconfirm_days` | 90 | 7–365 |
| `links_per_user` | 1 | 1–3 |
| `link_code_ttl_seconds` | 600 | 120–1800 |
| `init_data_max_age_seconds` | 300 | 60–3600 |
| `miniapp_session_idle_seconds` | 900 | 300–3600 |
| `miniapp_session_absolute_seconds` | 3600 | 900–43200 |
| `topics_mode_default` | off | stored but not read yet: the per-space `topics` setting is the switch |
| `notification_defaults` | see the guide | each link's starting notification preferences |

### Spaces

Per space: `enabled`, `content_level`, `enforced_approvals`, `topics`, `terminal_watch` and `group_chat_id` (see the
[guide](/guide/telegram#spaces-content-levels-and-the-terminal)). Writes need `space_config:write` in the space and a
step-up. A space with no row, or a disabled one, is invisible to Telegram.

#### Binding a group

Add the bot to a **forum** supergroup (topics on), then bind it:
`spaceman telegram set-space --space <space> --group-chat-id <negative chat ID>` (`0` unbinds). Binding, rebinding and
changing `group_chat_id` on a write (including `0`) need `telegram_group:write`, held by administrators only, on top of
`space_config:write`; other settings are unaffected and a write that leaves `group_chat_id` out keeps the binding. The bot
must be running (503 otherwise) and a member of the group, and the chat must be a forum supergroup (422 otherwise); a group
serves one space (409). Removing the space's Telegram settings (`space_config:write`, which operators hold) also unbinds
it. Bind within 15 minutes of adding the bot: an unbound forum group is left after that, and so is any
group whose binding is lost. For forms to open the Mini App from a group, set the bot's Main Mini App in BotFather. See
[Group mode](/guide/telegram#group-mode).

### Limits

`send_limits` bound what the bot sends and stay at or below Telegram's published limits (25 messages a second overall, one a
second per chat with a burst of 3, 20 a minute per group by default; the queue is bounded and drops the least urgent
first). `inbound_limits` bound what linked people can make central do (by default 30 updates a minute per link with a burst
of 10, 60 inbox items an hour, 50 downloads an hour, 20 updates a second overall). They are set with `--file` and take
effect without a restart. Excess gets one "slow down" answer.

Metrics for the webhook and the sender are in [Observability](/operators/observability#telegram-updates).

## Troubleshooting

- **The Mini App host answers 404.** Is `telegram.miniapp_host` set to the name Telegram is opening, and is the bot enabled
  and running (`spaceman telegram bot get`)? A 404 is the intended fail-closed answer.
- **"Session ended — close and reopen the app".** Sessions are in memory: they end after 15 minutes idle, an hour in all, a
  link change, a bot change or a restart.
- **Webhook shows an error.** Telegram needs HTTPS on an IPv4 route to the main host; try polling to separate the cases.
- **A person's account stopped working.** Their link may need re-confirming, may be capped lower, or was unlinked:
  `spaceman telegram links`.
